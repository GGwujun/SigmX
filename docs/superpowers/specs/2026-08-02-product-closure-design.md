# SigmX 产品闭环设计

**日期：** 2026-08-02

**状态：** 已确认方向，等待书面规格复核

**目标：** 在细化选股、策略和研究功能之前，先建立在线网站、Data Hub、本地客户端之间清晰且可运营的产品闭环。

## 1. 产品原则

SigmX 采用“产品分离、平台能力共享”的架构。三个产品形态共享证券代码、数据集、指标、API、身份和权益契约，但不共享全部页面、运行状态和用户私有数据。

第一阶段的成功标准不是增加更多投研功能，而是让新用户完成以下完整路径：

1. 通过公开网站认识 SigmX；
2. 注册统一账号并查看套餐；
3. 使用激活码开通套餐；
4. 获得会员权益、Data Hub 配额和 AI 积分；
5. 下载并登录本地客户端；
6. 客户端使用同一身份连接 Data Hub；
7. 用户运行一次计费 AI 任务；
8. 账户中心显示正确的权益、积分、用量和流水；
9. 用户能够续期、升级或补充积分。

首个可运营版本使用激活码作为正式开通通道。订单和支付采用适配器契约，后续接入支付宝、微信或其他支付渠道时不改变会员、权益、积分和客户端协议。

## 2. 产品边界

### 2.1 在线网站

在线网站负责获客、轻量体验和商业关系：

- 面向搜索引擎开放的品牌首页、产品页、套餐页和下载页；
- 注册、登录、退出和密码管理；
- 套餐展示、激活码兑换、权益与积分中心；
- 轻量公共市场内容和报告样例；
- 云端 AI 任务入口及历史记录；
- 客户端下载、版本信息和安装指引；
- 运营后台的用户、套餐、激活码、积分和 Data Hub 用量管理。

在线网站不保存券商密钥、本地文件、本地模型密钥或未经用户主动上传的持仓数据。

### 2.2 Data Hub

Data Hub 只负责公共金融数据及其公共计算结果：

- 行情、财务、新闻、公告、事件、行业和概念；
- 公共指标、市场宽度、资金流、热门池和公共推荐结果；
- 数据采集、标准化、去重、质量校验、版本和新鲜度；
- 供网站和客户端使用的只读 API；
- 基于权益的接口访问、每日配额、速率限制和用量记录；
- 后续对开发者和企业客户开放的外部 API。

Data Hub 不管理用户持仓、自选股、会话、私人报告、订单、模型配置或交易授权。Data Hub API Key 不能访问上述数据。

### 2.3 本地客户端

本地客户端负责用户私有、长时运行和本地计算能力：

- 私有持仓、自选股、交易日志和上传文件；
- 本地报告、策略、回测和定时任务；
- 用户自带模型 Key 或本地模型；
- 本地提醒、通知和券商连接；
- Standalone 模式下使用本地数据源；
- Connected 模式下通过统一权益令牌访问 Data Hub；
- 用户明确选择后才上传云端 AI 任务所需数据。

客户端不承担会员收款和公共数据的全市场采集。会员购买统一跳转在线网站完成。

### 2.4 后台平台能力

以下能力属于后台服务，不作为新的用户产品入口：

- Identity：统一用户身份和设备会话；
- Commerce：套餐目录、订单、激活和支付适配；
- Entitlement：功能、数据、席位和配额判定；
- Credit Ledger：积分发放、消耗、退款和到期；
- Cloud AI：SigmX 托管模型及异步任务；
- Operations：运营管理和审计。

## 3. 统一身份与数据归属

### 3.1 身份

- 网站账号是唯一的云端身份源；
- 客户端使用设备授权流程登录同一账号，不复制用户密码；
- 访问令牌短期有效，刷新令牌绑定设备并支持撤销；
- 一个账号的设备数量由套餐权益控制；
- Data Hub 接受由账户服务签发的权益令牌；现有 `sx_` API Key 保留给外部开发者和企业集成。

### 3.2 数据归属

| 数据 | 权威存储位置 | 同步规则 |
|---|---|---|
| 用户、套餐、订单、积分流水 | 云端账户服务 | 网站和客户端只读展示或通过 API 修改 |
| 公共金融数据 | Data Hub | 网站和 Connected 客户端只读 |
| 自选、持仓、券商授权 | 本地客户端 | 默认不同步 |
| 本地报告、回测、文件 | 本地客户端 | 默认不同步，用户主动分享时上传副本 |
| 云端 AI 任务和云报告 | 云端 AI 服务 | 用户主动提交后保存 |
| Standalone 行情库 | 本地客户端 | 不回传 Data Hub |

## 4. 套餐和积分

### 4.1 初始套餐目录

套餐参数保存在服务端目录中，前端不得硬编码价格或额度。

| 套餐 | 标价 | Data Hub | 每月套餐积分 | 设备数 | 主要用途 |
|---|---:|---:|---:|---:|---|
| 免费版 | 0 元 | 100 请求/日，基础数据 | 首次注册 50 积分 | 1 | 体验与本地基础功能 |
| 进阶版 | 268 元/季 | 1,000 请求/日，完整基础数据 | 300 积分/月 | 1 | 普通个人投资者 |
| 专业版 | 518 元/季 | 10,000 请求/日，特色数据 | 1,200 积分/月 | 3 | 重度研究和批量任务 |
| 企业版 | 合同报价 | 独立额度和 SLA | 合同配置 | 合同配置 | API、团队和私有化 |

金额和额度是初始运营值，可由后台变更；订单需要保存购买时的价格与权益快照，避免目录更新改变历史订单。

### 4.2 积分规则

- 套餐积分按自然月发放并在当月结束时失效；
- 免费版 50 积分只在首次注册时发放一次；
- 额外购买或管理员补偿的积分不设过期时间；
- 扣减顺序为最早过期积分优先，其次永久积分；
- AlphaForge 维持 50 积分/次，基金套利维持 20 积分/次；
- 云端任务在提交时原子预扣，成功后结算，失败或取消后幂等退款；
- 用户自带模型 Key 或本地模型在本机执行时不消耗云端积分；
- 所有积分变化写入不可变流水，余额由流水汇总或事务性余额缓存得到。

## 5. 商业与激活流程

### 5.1 首发激活码流程

1. 运营后台按套餐、有效期和数量生成激活码；
2. 用户在网站账户中心输入激活码；
3. Commerce 创建金额为零、渠道为 `activation_code` 的已支付订单；
4. Entitlement 创建或延长会员周期；
5. Credit Ledger 发放当前月套餐积分；
6. Data Hub 权益立即生效；
7. 客户端刷新令牌后显示新套餐和额度。

同一激活码只能成功使用一次。重复请求必须返回第一次的订单结果，不能重复发放权益。

### 5.2 支付适配器契约

支付适配器统一提供：

- `create_checkout(order)`：创建支付会话；
- `verify_webhook(headers, body)`：验证回调；
- `parse_event(body)`：转换为标准支付事件；
- `query_payment(provider_payment_id)`：主动查单；
- `refund(provider_payment_id, amount)`：退款。

首发实现 `activation_code` 适配器。真实支付适配器只能通过签名回调或主动查单把订单置为已支付，前端跳转结果不能直接开通权益。

## 6. 权益判定

所有产品使用稳定的权益键，不在业务代码中判断中文套餐名称：

- `datahub.basic`
- `datahub.featured`
- `datahub.external_api`
- `cloud_ai.enabled`
- `cloud_ai.concurrent_jobs`
- `desktop.connected_mode`
- `desktop.device_limit`
- `reports.cloud_history`
- `admin.operations`

权益服务返回当前套餐、有效期、功能键、数值配额和积分余额。客户端缓存最近一次成功结果，但需要云端授权的操作必须由服务端再次校验。

## 7. 最小页面结构

### 7.1 公开网站

- `/`：品牌价值、三个产品形态、示例结果和主要行动按钮；
- `/product/data-hub`：Data Hub 数据质量和 Connected 模式；
- `/product/desktop`：客户端价值、系统要求和下载；
- `/pricing`：四档套餐和权益对比；
- `/download`：稳定版版本号、安装包和更新说明；
- `/reports/sample/:slug`：脱敏公开报告样例；
- `/login`、`/register`：身份入口。

### 7.2 登录后网站

- `/app`：轻量工作台；
- `/account/subscription`：套餐、有效期、激活与升级；
- `/account/credits`：积分余额、到期批次和流水；
- `/account/usage`：Data Hub 与云端 AI 用量；
- `/account/devices`：设备列表和撤销；
- `/account/orders`：订单历史；
- `/admin/operations`：运营后台。

### 7.3 客户端

现有投研页面暂不重做，只增加统一的产品状态区：

- 当前账号和套餐；
- Data Hub 的 Standalone/Connected 状态；
- 积分余额与即将到期数量；
- 数据额度和今日用量；
- 设备授权状态；
- 前往网站购买、续期和管理账户的入口。

## 8. 服务边界和迁移路径

第一阶段保持现有 Python/FastAPI、React、Electron 技术栈，不进行微服务拆分。边界通过独立模块、数据库表和 API 前缀表达，降低部署复杂度：

- `/api/account/*`：统一账户；
- `/api/catalog/*`：套餐目录；
- `/api/orders/*`：订单和激活；
- `/api/entitlements/*`：权益查询；
- `/api/credits/*`：积分；
- `/api/devices/*`：设备授权；
- `/api/v1/*`：Data Hub 公共数据；
- `/api/admin/*`：运营接口。

第一阶段云端商业数据使用独立 SQLite 数据库和事务，避免干扰现有本地数据库。部署规模需要横向扩展前，再通过存储接口迁移到 PostgreSQL。客户端私有存储继续使用本地 SQLite/JSON；本阶段不统一其内部自选和持仓模型。

现有积分余额迁移为永久积分批次；现有 Data Hub Free/Basic/Pro 映射为免费版、进阶版、专业版。现有 `sx_` API Key 不失效。

## 9. 安全、审计与失败处理

- 密码继续使用安全哈希，不记录明文；
- 激活码和 API Key 只存哈希，明文只在创建时展示；
- 刷新令牌按设备存储哈希并支持撤销；
- 订单支付、激活、权益发放和积分发放使用同一事务或可重放状态机；
- 每个外部回调、激活请求和积分预扣都具有幂等键；
- Data Hub 同时校验有效期、权益和配额；
- 管理员调整积分、撤销设备、封禁订阅必须写审计日志；
- 云端不可用时，本地 Standalone 功能继续运行；Connected 数据与云端 AI 明确显示不可用，不静默读取陈旧数据冒充最新数据。

## 10. 实施顺序

1. 建立套餐目录、权益、订单、积分批次和设备授权领域模型；
2. 兼容迁移现有用户、积分和 Data Hub 订阅；
3. 建立网站公开页面和账户商业中心；
4. 打通激活码到订单、权益、积分和 Data Hub 的原子流程；
5. 改造客户端登录、设备授权和产品状态区；
6. 完成 Data Hub 权益令牌与现有 API Key 双鉴权；
7. 建立运营后台和审计；
8. 完成端到端闭环测试、升级测试和失败恢复测试。

## 11. 测试与验收

至少覆盖：

- 注册后只获得一次免费积分；
- 激活码重复提交不重复创建权益或积分；
- 进阶版和专业版获得正确的 Data Hub 配额；
- 套餐积分到期，永久积分不受影响；
- AI 任务失败只退款一次；
- 客户端设备数达到上限后拒绝新设备；
- 撤销设备后刷新令牌立即失效；
- 套餐过期后 Connected 模式降级并提示，不泄漏特色数据；
- 现有 Data Hub API Key 和现有积分余额迁移后仍可用；
- 网站、客户端、Data Hub 对同一账号返回一致的套餐和余额；
- Data Hub 离线时客户端 Standalone 功能不受影响。

闭环验收使用一个全新账号完成：注册、激活进阶版、登录客户端、连接 Data Hub、运行一次 AlphaForge、查看扣费流水、撤销设备和重新登录。所有步骤必须通过公开 UI 完成，运营人员只负责预先生成激活码。

## 12. 非目标

本设计周期不包含自然语言选股、策略商城、社区作者体系、指标扩充、页面视觉大改、企业团队空间、全部本地数据云同步和自动交易能力优化。这些功能只能在产品闭环通过验收后进入后续设计周期。
