# SigmX 完整产品实现修订设计

> 日期：2026-08-16  
> 状态：已批准，直接实施  
> 基线：[SigmX 产品总架构设计](./2026-08-15-sigmx-product-architecture-design.md)  
> 范围：个人用户；不接入支付宝、微信等真实支付，保留激活码兑换

## 1. 修订目的

现有实现证明了账户、权益、双积分、Data Hub 网关、Web 公开页和 Desktop Harness 适配层的技术可行性，但大量页面停留在“接口接通 + 卡片展示”，不能证明总架构设计已经成为完整产品。本设计不缩小原始范围，而是定义可执行、可验收的完成标准。

完成不再以路由、DTO 或单元测试存在为依据。每项能力必须同时具备真实领域数据、完整主操作、状态变化、失败和降级处理、可追溯性、页面级交互以及端到端验收证据。

## 2. 产品边界

SigmX 保持三个产品面：

1. **Web**：官网、流量入口、公开研究、个人中心、账户与 Data Hub 控制台。
2. **Desktop Financial Harness**：本地优先的专业金融研究运行环境。
3. **Data Hub**：可随套餐授权、也可通过独立 Data Credit 包使用的数据服务。

Web 和 Desktop 在同一仓库开发，但拥有独立入口、路由壳、状态边界、构建产物和发布流程。二者只共享设计系统、领域类型和 API Client，禁止继续用运行时环境判断隐藏另一产品的页面。

建议代码边界：

```text
apps/web/                 Web 入口、路由和页面
apps/desktop/             Desktop 入口、路由和页面
packages/ui/              设计令牌与通用组件
packages/domain/          共享领域类型与校验
packages/api-client/      cloud/local 两套客户端
desktop/                  Electron 主进程与安装包
agent/                    Python 云端与本地运行时
datahub-python/           独立 Python SDK
```

Electron 只能加载 Desktop 构建产物；生产网站只能发布 Web 构建产物。

## 3. 体验方向

整体采用“专业机构级金融终端”语言：高信息密度、克制深色、清晰数据层级、表格/图表/时间线优先。减少大面积营销卡片和装饰数字。

所有数据组件统一呈现：

- 数据时间、来源、延迟和质量；
- 加载、空数据、无权限、积分不足、失败和降级状态；
- 主操作执行前影响，执行后结果与下一步；
- 可访问的键盘焦点、语义标签和基本响应式行为。

## 4. Web 完整设计

### 4.1 公共发现层

- **首页**：市场状态、热门主题、示例问题、代表性研究、Desktop 和 Data Hub 产品入口。
- **统一搜索**：证券代码/名称、自然语言筛选、ETF/LOF、市场问题和 API 文档；识别查询意图并进入相应结果形态。
- **查询结果**：解析条件、结果表格、排序、数据时间与质量、保存查询、订阅和分享。
- **股票详情**：行情、估值、财务趋势、资金、事件、风险、AI 摘要、数据质量、云自选和 Desktop 深研交接。
- **基金详情**：行情/净值、跟踪标的、折溢价、规模、流动性、持仓、套利信息、风险和 Desktop 交接。
- **公开研究**：结构化结论、证据引用、数据版本、风险、失效条件和分享链接。
- **产品闭环**：产品、套餐、下载、Data Hub 文档与注册入口互相连通，并记录完整漏斗。

### 4.2 登录后个人中心

`/me` 是“今日研究驾驶舱”，不是账户卡片集合：

- 今日市场变化、关注事件、订阅命中和积分到期；
- 云自选的分组、排序、备注、提醒和双向同步；
- 保存查询、执行历史、条件版本、订阅频率和最近命中；
- 云报告的状态、来源、结论、更新时间和 Desktop 继续入口；
- 云任务的排队、运行、成功、失败、取消、积分预占/结算/退款；
- 站内通知、已读状态、渠道偏好和订阅规则；
- Desktop 设备在线状态、心跳、版本、授权和一键交接。

### 4.3 账户与 Data Hub

- 套餐、权益、Research Credit/Data Credit 余额、批次和账本；
- 激活码兑换、订单记录、设备、会话和账户安全；
- Data Hub 引导、Credential、Scope、IP 白名单、轮换和吊销；
- 接口目录、结构化参数、在线调试、SDK 快速开始；
- 用量趋势、请求日志、错误详情、预算和告警。

## 5. Desktop Financial Harness 完整设计

Desktop 不是网页外壳，而是由六个运行时共同构成的研究环境：Agent、Data、Tool、Context、Governance、Observability。

### 5.1 一级信息架构

- **今日**：市场环境、关注事件、待继续研究、最近运行、数据健康。
- **研究中心**：对话研究、任务计划、证据面板、结论编辑和报告输出。
- **市场工作台**：行情、市场阶段、新闻事件、资金和机会发现。
- **量化实验室**：因子、回测、对比、相关性、策略实验和结果版本。
- **跟踪中心**：自选、定时任务、信号、提醒和推荐历史。
- **运行中心**：Agent、Swarm、回测和云任务的统一 Harness Run。
- **本地资产**：数据集、研究文件、报告、缓存和数据版本。
- **云连接**：账户、权益、同步、Data Hub、设备和积分。
- **设置**：模型、数据源、工具权限、隐私、通知、更新和诊断。

### 5.2 统一 Harness Run

当前 Session、Swarm、AlphaForge、基金套利和定时分析必须写入同一权威运行模型，而非只读拼装。每个 Run 包含：

- 目标、类型、状态和生命周期；
- Context Manifest 与数据版本；
- 计划、步骤、Tool Call 和耗时；
- Evidence、Artifact、结论和结果引用；
- Research Credit、Data Credit 和本地计算成本；
- 失败、降级、重试及治理确认记录；
- 复现、继续、复制和导出能力。

### 5.3 本地与云连接

- Standalone 支持本地数据、文件、Agent 和运行历史；
- Connected 增加云自选、报告、任务、Data Hub 和 Web 交接；
- 断网不阻塞本地研究，云能力明确降级；
- 恢复连接后增量同步，冲突必须可见且不得静默覆盖；
- 本地文件只上传安全引用或用户明确选择的内容。

## 6. Data Hub 完整设计

### 6.1 产品能力

- Basic、Market、Finance、Pro 四级接口组；
- 套餐控制接口范围、历史深度、单次行数、频率和 Data Credit 上限；
- 接口采用版本化免费/固定/按结果量计价；
- 请求前校验权限、预算和最大可能费用，响应后按有效结果结算；
- 超时或服务错误不扣分，部分结果按有效结果计费并显式降级；
- 响应统一返回来源、交易日、复权方式、版本、更新时间和质量标志；
- 多源归一、去重、复权、交易日、异常检测和来源回退进入真实链路；
- Python SDK 覆盖认证、重试、分页、错误类型、用量响应头和示例。

### 6.2 开发者控制台

控制台拆分为概览、Credentials、接口目录、在线调试、用量、日志、预算告警、SDK/文档和积分九个清晰页面，取代当前单页堆叠。

## 7. 个人产品运营后台

后台覆盖：

- 用户、状态、套餐、积分、设备、安全操作；
- 套餐、权益、Data Credit 包、价格和上下架；
- 激活码订单、人工撤销/退款记录；
- 激活码批次、领取、使用、过期和审计；
- 双积分人工调整及强制原因；
- Data Hub 接口、版本、定价、开关、成本和质量；
- 主题、示例查询、公开报告和首页运营位；
- 完整漏斗、激活、留存、使用、升级意向、分享、消耗和毛利估算。

所有后台写操作记录操作者、时间、原因和前后值。

## 8. 统一领域对象与不变量

核心对象：User、Plan、Entitlement、Device、Order、ActivationCode、双积分 Lot/Ledger、SavedQuery、QueryExecution、Watchlist、ResearchReport、CloudTask、HarnessRun、ContextManifest、ToolCall、Evidence、Artifact、DataCredential、EndpointCatalog、UsageRecord、Budget、QualityRecord、Notification、Subscription、AuditLog、FunnelEvent。

不变量：

- 双积分账本不可变，云任务使用预占、结算、退款状态机；
- Web 与 Desktop 不共享页面状态，只同步领域对象；
- 数据版本、证据、运行和后台变更可追溯；
- 降级必须显式，空数据不得伪装成功；
- 激活码明文只展示一次且不落库；
- 不实现真实支付，但支付适配协议可以保留。

## 9. 交付顺序

1. 建立需求—证据矩阵与独立前端边界；
2. 完成共享设计系统和统一页面状态；
3. 完成 Web 公共发现与增长闭环；
4. 完成个人中心、云任务和 Desktop 连接；
5. 完成 Desktop 信息架构和统一 Harness Run；
6. 完成 Data Hub 数据质量、SDK 和控制台；
7. 完成个人产品运营后台；
8. 全量自动化、浏览器、Electron 打包和生产验收；
9. 逐条回审原总架构文档，缺少直接证据的条目一律不得标记完成。

## 10. 完成定义

只有同时满足以下条件才可宣称完整实现：

- 原总架构文档每项要求均有代码、测试和运行时证据；
- Web 与 Desktop 分别构建，发布物不包含对方路由；
- 所有核心页面具备真实数据、完整操作和异常/降级状态；
- 三个关键闭环通过端到端测试：Web→注册/沉淀、Web→Desktop、Data Hub→积分结算；
- Desktop 的全部研究类型进入权威 Harness Run；
- Data Hub 数据质量元数据可在 API、SDK 和控制台观察；
- 运营后台支持原设计列出的个人产品运营工作；
- 前后端测试、浏览器验收、Desktop 打包和生产健康检查通过；
- 证据矩阵由实际检查结果生成，不以文件存在或窄测试代替产品完成度。
